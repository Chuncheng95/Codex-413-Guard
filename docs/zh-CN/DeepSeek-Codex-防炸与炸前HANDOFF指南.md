# 第三方网关下的 Codex 会话预警与炸前 HANDOFF

> 文件名保留了最初的 DeepSeek 使用场景，但本文方法面向的是“Codex + 第三方或自建
> 网关”这一类部署。不同入口的真实限制可能不同，也可能随配置和时间变化。

[English version](../en/codex-third-party-gateway-prevention-and-handoff.md)

## 为什么 HANDOFF 比事后修复更重要

HTTP 413 往往由模型之前的代理层直接返回。如果每次继续请求仍携带同一份过大的历史，
原会话可能无法再让模型替你总结工作。这时能否顺利接手，取决于重要状态是否已经写入
会话之外的项目文件。

所以推荐顺序是：

1. 平时观察本地会话增长趋势；
2. 在阶段节点写 HANDOFF；
3. 风险升高后减少截图或开启新会话；
4. 修复脚本只作为最后保险。

## 哪些工作流增长更快

- 浏览器或 computer-use 持续截图；
- 同一画面反复截图确认；
- 图片生成、抠图、视觉审核；
- 工具把图片以内联 base64 返回，而不是只给文件路径；
- 很长时间不换会话的视觉任务。

不能用“截图 40 张”或“100 张一定会出事”作通用规则。图片尺寸、编码、重复方式、客户端
历史处理和网关配置都会改变结果。

## 使用体检脚本

```bash
python3 scripts/session_health.py --list
python3 scripts/session_health.py --list --deep
python3 scripts/session_health.py --session <会话ID>
```

快速模式只看本地文件体积；`--deep` 解析 JSONL 并统计脚本认识的图片结构。

默认 20 MB 和 35 MB 是提醒线，不是服务规格：

- `low`：继续工作，但阶段结束仍建议交接；
- `warning`：现在写 HANDOFF，减少新的视觉负载；
- `high`：优先换会话或先做受控瘦身，不再继续堆图。

已知自己的入口行为时，可以调整：

```bash
python3 scripts/session_health.py --list --warn-mb 25 --critical-mb 40
```

脚本不能保证自动知道哪个 rollout 就是界面里“当前会话”，所以需要用会话 ID、时间戳和
用户自己的上下文核对，不能让 Agent 猜测后直接操作。

## 一份好用的 HANDOFF 应该写什么

```markdown
# HANDOFF

## 1. 当前目标
一句话说清完成标准。

## 2. 已确认事实与证据
只写已经验证的结论，并附仓库相对路径、测试名或简短数据。

## 3. 已改动文件
逐项写相对路径和改动目的。

## 4. 未完成事项与卡点
按优先级列出，说明哪些需要用户选择。

## 5. 下一步可执行动作
让新会话可以从第一步直接开始。

## 6. 关键上下文与踩坑
记录失败过的方法和不能破坏的约束。

## 7. 相关素材位置
只写项目内相对路径，不复制图片或日志正文。
```

取得内置提示词：

```bash
python3 scripts/session_health.py --handoff-prompt zh
```

HANDOFF 不应该包含 API 密钥、令牌、真实会话 UUID、用户目录、完整日志、base64 或私人
图片。它是交接摘要，不是把整个会话再复制一遍。

## 新会话接手流程

新会话开场：

```text
请读取 .codex-handoff/HANDOFF.md。先复述当前目标、已经完成的内容和下一步第 1 项；
指出仍需我确认的地方，再继续执行。不要重复生成已有产物。
```

接手后先核对工作区实际状态。HANDOFF 可能滞后，也可能记录了当时的错误判断；文件系统、
测试结果和用户最新指示优先。

## AGENTS.md 能做什么，不能做什么

[示例规则](../../examples/AGENTS.md) 可以让 Agent 在阶段结束、截图密集后或体检达到提醒线
时主动写 HANDOFF。它适合建立纪律，但不是守护进程：

- 不会因为写进文件就每小时自动运行；
- 不会自动获得 HTTP 请求体大小；
- 不会保证精确定位当前 rollout；
- 没有脚本结果时不能声称“已达到上限 70%”。

如果确实需要定时任务，应由用户显式配置系统调度器或 Codex Automation。通知策略最好是
风险等级发生变化、检查失败或需要用户行动时才提醒；状态不变时保持安静。

## 六个减慢增长的做法

1. 让视觉工具优先把图片保存到工作区，只返回路径和必要摘要。
2. 截图前先说明需要观察什么，减少盲目连拍。
3. 把视觉探索和代码实现拆成不同会话。
4. 一个阶段结束就更新 HANDOFF，不等体积提醒。
5. 对旧截图只保留项目所需产物，不在新消息中反复内联。
6. 到达 warning 后开新会话通常比继续赌下一轮更稳。

## 如果已经出现 413

不要继续让原会话“再总结一次”。先读
[完整恢复文章](Codex-413-会话卡死修复指南.md)，用只读诊断确认故障，再生成新 ID 的备份
副本并做分层验证。

简明 HANDOFF 版见 [预警与 HANDOFF 指南](HANDOFF.md)。
